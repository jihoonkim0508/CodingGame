# CodingGame 개발명세서

작성일: 2026-09-18 · 버전: 0.1 · 상태: 구현 검토용 초안

> **현재 기준 갱신:** 킹덤러쉬를 참고한 자유 배치·거리 기반 디펜스를 먼저 구현한다. 최신 기준은 [디펜스 기능서 v0.2](디펜스_기능서.md)다. 타일/방향별 칸 사거리 대신 실제 거리를 사용하고, 일반 로봇은 무체력이며 탱커만 적 경로 설치·HP·몸 저지·스턴을 가진다. 연사형은 사거리/공격력 반비례·단발이다. 명령어는 `block()`으로 통일한다. 원거리형의 `block()`과 탱커의 `buff()`는 편집 배치 가능·실행 무효이며 전체 호환표는 미정이다.

> **이하 본문은 이전 통합 계약의 기록이다.** 기존 로봇 종류·고정 콘텐츠 수·배치/공격/체력/사거리 규칙과 테스트 기대값은 최신 기능서와 충돌하면 폐기한다. 코딩 통합 계약은 후속 참고이며, Python 실행기와 콘텐츠 확정을 디펜스 기반의 착수·완료 조건으로 삼지 않는다. 비용·퇴각·재배치 정책은 새 기획에서 재확인한다.

상위 문서: [개발문서](개발문서.md). 원본 세 자료와 P/U/A 표기, D01~D18 결정 목록은 상위 문서에서 관리한다. **원문에서 결정되지 않은 세부 동작은 모두 제안 계약이며, 구현 완료 또는 승인 상태를 뜻하지 않는다.**

## 1. 구현 범위와 기준

## 2. 상태 및 웨이브 계약

아래 상태명과 우선순위는 제안이다. 시간은 게임 진행 시간을 사용하고, 일시정지를 도입하면 전투·정비 타이머도 함께 정지한다.

| 상태 | 진입 작업 | 허용 입력 | 종료 조건 / 다음 상태 |
|---|---|---|---|
| StageIntro | 학습 목표·새 블록 안내, 스테이지 데이터 읽기 | 안내 진행 | 안내 완료 → 첫 Combat. 첫 전투 지급은 D14 |
| Combat | 스폰 스케줄 시작, 로봇 실행기 가동 | 로봇 선택·상태 열람, 개발툴 스킬(입력 방식 미정) | 모든 스폰 처리 및 생존 적 0 → 정비/클리어; 오류 임계치 → GameOver |
| Maintenance | 전투 실행 정지, 수량·함수·배치 편집 허용 | 블록 편집, 적용, 로봇 배치/이동/삭제, 다음 웨이브 | 시간 만료 또는 유효한 시작 요청 → Combat |
| StageClear | 승리 처리, 전투 입력 차단 | 결과 확인 | 다음 스테이지 → StageIntro; 마지막 → Victory |
| GameOver | 스폰·실행·추가 보상 중지 | 처음부터 재도전 | 세션 초기화 → 첫 StageIntro |
| Victory | 최종 결과 확정, 전투 정지 | 결과 확인·처음부터 | 재시작 시 초기화 |

### 2.1 웨이브 종료 제안

1. 스폰 예정 수, 스폰 완료 수, 취소 수, 생존 수를 별도로 추적한다.
2. `스폰 완료 수 + 취소 수 = 예정 수`이고 `생존 수 = 0`일 때만 정상 종료한다.
3. 제한시간에 아직 생성하지 않은 적은 취소한다(P p.4). 이미 생성된 적은 계속 이동·전투하고, 모두 처치 또는 침입해야 종료하는 안을 사용한다(D02).
4. 같은 시뮬레이션 틱의 피해·사망·침입을 확정한 후 실패를 먼저 검사한다. 실패가 없을 때 마지막 웨이브 클리어를 검사한다.
5. 5번째 웨이브 뒤에는 정비 없이 결과로 간다. 다음 웨이브 버튼을 여러 번 눌러도 전환은 한 번만 실행한다.
6. 정비 종료 시 적용하지 않은 초안은 실행하지 않는다. 유효한 기존 적용본을 사용하고 미적용 안내를 표시한다. 함수 없는 로봇은 대기한다. 첫 전투 기본 함수와 정비 시간 정책은 D03/D14로 확정한다.

적 수 원식 `stage × 2.5`, 로봇 상한 원식 `stage × 1.25`는 그대로 기록하되 런타임에서는 명시된 정수 데이터로 읽는 것을 제안한다. 초안 올림 값은 각각 `[3,5,8,10]`, `[2,3,4,5]`이며 확정 밸런스가 아니다. 웨이브별 증가량·스폰 간격은 제공되지 않았다.

## 3. 블록 언어와 검증

### 3.1 편집 모델

현재 `CodeBlock.Kind`, `Value`, `Arguments`, `Body` 모델을 기반으로 한다. `Arguments`는 입력 식, `Body`는 제어문 내부 문장이다. 실행 순서는 화면 좌표 정렬이 아닌 실제 연결 구조로 결정한다. 자유 배치된 미연결 조각을 조용히 제외하지 않는다. 이는 D05의 현 편집기 유지 제안이며 고정 슬롯 요구와의 차이는 상위 문서에 명시했다.

| 블록 | 입력/출력 | 검증 및 동작 제안 |
|---|---|---|
| 변수 선언 | 이름 + 값 → 문장 | Python 식별자, 예약어/API 이름 금지, 사용 전 정의 |
| 숫자 | 사용자 입력 → int/float | 불완전 입력은 적용 차단. 값 범위·음수·소수는 D10 |
| 비교 | 수치 2개 + 연산자 → bool | >, <, >=, <=, ==. 호환되지 않는 타입 거부 |
| if / elif / else | 조건 + 본문 | 같은 깊이의 연결된 분기만 허용. else 조건 불허 |
| for | 정수 반복 횟수 + 본문 | range(n), n은 0 이상 정수. 실수 횟수 거부, 상한은 데이터 |
| while | 조건 + 본문이라는 원문 목표 | 현재 편집기는 조건 없는 while True. D07 결정 전 완료 처리 금지 |
| Attack / Wait | 행동 문장 | 인자 및 시간 의미는 아래 API 결정에 따름 |
| 적 정보 | 거리·HP·수·속도 → 수치 | 단위·관찰 대상·적 없는 경우를 일관되게 정의 |

빈 함수와 빈 제어 본문은 현재 컴파일러에서 `pass`로 표시할 수 있다. 게임 적용 단계에서는 학습 과제와 행동 유무를 추가 검사할 것을 제안한다. 빈 본문을 곧바로 Python 문법 오류라고 표시하지 않는다.

### 3.2 단계별 검사

| 단계 | 검사 | 실패 피드백 |
|---|---|---|
| 구조 | 단일 연결 흐름, 입력 슬롯, 분기 순서, 자기 포함 금지 | 문제 블록 강조 + 적용 비활성 |
| 타입/문법 | 변수 정의, 숫자, 비교 타입, 인자 수, 들여쓰기 | 블록 ID와 코드 행을 연결해 이유 표시 |
| 학습 과제 | 스테이지 2의 조건문 내부 Attack 등 | 문법 오류와 구별한 `학습 조건 미충족` |
| 자원 | 사용 블록 수량, 로봇 유효성, 편집 가능 상태 | 부족 종류·수량 또는 상태 안내 |
| 실행 보호 | 연산·반복 한도, 실행 중 잘못된 참조 | 해당 로봇 함수 정지, 원인 표시, 게임 루프는 계속 |

스테이지 2는 최소 한 Attack이 if/elif/else 분기 내부에 있는지 확인하는 안이다. 조건문 밖의 추가 Attack 허용 여부와 상수 True 조건 인정 여부는 콘텐츠 확정 시 결정한다. 스테이지 3·4의 강제 구조 검사는 원문에 명확히 없으므로 학습 목표와 실행 금지를 혼동하지 않는다.

### 3.3 API 차이와 결정안

| 기능 | 원문·UI 표현 | 현재 소스 표현 | 필요한 결정 |
|---|---|---|---|
| 공격 | `Attack()` | `attack(enemy)` | 암묵 타겟 또는 명시 타겟, 대소문자 통일 |
| 대기 | `Wait()` | `wait(seconds)` | 기본 대기 시간 또는 인자 입력 |
| 적 선택 | `Enemy` 정보 블록 | `get_nearest_enemy()` | Enemy 정보 집합과 객체 변수 중 교육 모델 선택 |
| 거리 | `Enemy.Distance` | `enemy.get_distance(x,y)` | 자동 거리 또는 좌표 인자, 좌표계 통일 |
| 기타 정보 | `Enemy.HP/Count/Speed` | 현재 enum·Enemy 클래스에서 동일 API 미확인 | 명시적으로 추가 설계·구현 필요 |
| 반복 | 조건부 while 예시 | 인자 없는 `while True:` 지원 | 조건 슬롯 추가 또는 학습 예제 변경 |

**D08 권장안:** 게임에서는 허용된 블록 트리만 C#으로 해석하고 같은 트리에서 Python 텍스트를 생성한다. CPython 내장 실행, 외부 프로세스, 임의 문자열 `eval`은 자동으로 도입하지 않는다. 실제 Python 인터프리터 실행 자체가 요구라면 지원 플랫폼·배포·중단 방법을 별도로 검증한다. 이 권장안은 Python 전체 언어 지원을 뜻하지 않는다.

다음은 원문 표기를 유지한 **목표 예제**이며 현 컴파일러에서 그대로 생성된 출력이 아니다.

```python
def defend():
    if Enemy.Distance < 10:
        Attack()
    else:
        Wait()
```

위 함수의 자동 재호출은 게임 실행기가 수행한다. 플레이어 함수 본문에 숨은 `while True`를 삽입해 Python 코드와 실제 제어 흐름을 다르게 보이게 하지 않는다. 실행 상태 UI에 `함수 끝 → 처음부터 재실행`을 설명한다.

## 4. 함수 실행과 전투 계약 제안

### 4.1 실행기

로봇별 실행기는 `Idle / Running / Waiting / Faulted` 상태, 적용본 버전, 현재 블록 ID, 지역 변수, 제어 스택, 대기 종료 시각을 가진다. 데이터 교체는 정비에서만 이루어지는 것을 기본안으로 한다.

- 함수 호출 시 지역 변수를 초기화한다. 본문 종료 후 다음 시뮬레이션 틱에 다시 호출한다. 영구 누적 변수는 별도 요구가 없으므로 추가하지 않는다.
- 조건·비교·대입은 같은 틱에 평가하되 틱당 노드 처리 예산을 적용한다.
- **Attack 제안:** 유효한 범위 내 타겟에 1회 사격하고, 해당 로봇의 1초 공격 간격이 찰 때까지 다음 실행을 기다린다. 재호출·반복문으로 이 간격을 우회할 수 없다.
- 타겟이 없거나 범위 밖이면 공격하지 않고 최소 다음 틱으로 넘긴다. 탄환·피해를 만들지 않는다.
- **Wait 제안:** 선택된 API의 대기 시간 동안 실행을 양보한다. 인자 없는 표기는 기본값 확정이 필요하다. wait(0)도 최소 다음 틱으로 넘긴다.
- for는 반복 횟수를 순서대로 수행하며 Attack/Wait의 시간 경과를 따른다.
- 조건부 while은 매 반복 시 조건을 다시 평가한다. 모든 무한 루프를 사전에 판정할 수 있다고 가정하지 않는다. 명백한 비양보 루프는 적용 전에 거부하고 실행 중에도 예산으로 보호한다.

이 동작은 원문의 `즉시 반복` 및 `Attack 실행 시 계속 발사` 문구를 구체화하는 **대체 해석안**이다. D07 승인 없이 확정 구현으로 사용하지 않는다. 특히 Attack이 영구 공격 모드를 켜는 명령이면 이후 조건문·Wait로 공격을 중단하는 규칙을 다시 설계해야 한다.

초기 보호값 제안: 로봇당 틱 처리 200노드, 중첩 깊이 16, 한 번의 함수 호출 10,000노드. 초과 시 게임 전체를 멈추지 않고 해당 함수만 Faulted 처리한다. 장기 실행하는 정상 while도 총 한도에 도달할 수 있음을 UI에서 알리고 실제 콘텐츠로 조정한다. 이 값은 성능 측정 결과가 아니다.

### 4.2 타겟과 적 정보

- 타겟 후보: 활성 상태이며 사망·침입 처리되지 않은 적. 공격 판단은 인식 범위와 실제 공격 범위를 통과해야 한다.
- 가장 가까운 적은 로봇 기준 평면 거리로 선택하고 동률이면 생성 순번이 작은 적을 택하는 안이다.
- 조건문 평가와 그에 따른 행동까지 동일 타겟 스냅샷을 사용한다. 행동 직전 타겟이 사라졌다면 재검증하고 공격을 건너뛴 뒤 다음 평가에서 재선정한다.
- 목표 3D 전장의 평면은 XZ를 제안한다. 현재 `Enemy.get_distance`는 XY 거리이므로, 게임 좌표 API를 정하고 함께 맞춰야 한다. 기존 코드를 문서 작성 중 변경하지 않는다.
- `Enemy.Distance`는 선택 타겟까지의 Unity 월드 단위 거리, `HP`는 남은 HP, `Speed`는 유효 월드 단위/초를 제안한다.
- `Enemy.Count`는 해당 로봇 인식 범위의 생존 적 수를 제안한다. 전체 맵 수와 구별하며 D08에서 확정한다.
- 적이 없을 때 원문형 정보 API는 Distance=∞, HP=0, Speed=0, Count=0으로 읽는 안이다. Attack은 별도로 타겟 유효성을 검사한다. 객체 API를 채택한다면 null 처리를 표현할 블록이 필요하므로 함께 결정한다.

### 4.3 피해·둔화·침입

로봇 공격력, 인식 범위, 실제 사거리, 공격 간격을 별도 필드로 둔다. 인식 범위가 늘수록 공격력이 감소하는 공격형 특성의 산식과 상한은 D12 확정 사항이다. 서폿형 피해와 둔화는 동일 피격 이벤트에 적용하고, 중첩은 가장 강한 둔화만 유지·지속시간 갱신하는 안을 제안한다.

적은 `Active → Killed` 또는 `Active → Leaked` 중 하나로 한 번만 전환한다. Killed만 드롭을 발생시키고 Leaked는 침입 오류량을 부여한 뒤 제거한다. 같은 틱에 사망과 도착이 겹치면 확정된 피해를 먼저 처리하고 이미 Killed인 적의 침입을 차단한다. 모든 전환은 적 ID로 중복 처리를 막는다.

탄환과 즉시 피해 중 표현 방식, 적 개별 수치, 서폿 둔화 수치, 보스 저항은 제공되지 않았으며 콘텐츠 데이터 확정이 필요하다.

## 5. 명령어 인벤토리와 적용 계약 제안

**수량 의미 제안:** 명령어 1개는 활성 함수에 같은 블록을 한 번 배치할 권리다. 실행할 때 소모하지 않는다. 이 해석을 D09에서 확정한다. for 본문에 Attack 1개를 넣어 3회 반복해도 Attack 예약은 1개다.

`잔여 수량 = 보유 수량 - 모든 로봇 적용본의 예약 수량 합`

초안은 예약을 즉시 변경하지 않는다. 로봇 함수 교체 검사는 `보유 - 다른 로봇 예약` 범위에서 새 함수 비용을 비교한다. 교체 성공 시 기존 예약을 해제하고 새 예약을 한 번에 반영한다. 중간 상태를 UI나 다른 로봇에 노출하지 않는다.

### 5.1 적용 절차

1. 선택 로봇과 정비 상태, 초안 버전을 확인한다.
2. 구조·문법·타입·학습·수량을 검증한다. 실패하면 초안에 이유를 표시한다.
3. 성공 시 수정 불가능한 블록 트리 복사본과 예약 수량을 만든다.
4. 기존 함수와 예약을 새 적용본으로 원자적으로 교체하고 실행 상태를 초기화한다.
5. 적용된 함수명·버전·로봇 상태를 갱신한다. 다음 전투에서 새 적용본을 실행한다.

실패 시 **기존 로봇 적용본과 예약은 유지**한다. 현재 `CommandCodingPanel.AppliedSource`는 편집 변경이나 적용 실패 시 비워지는 표시용 상태이므로, 향후 전투 적용본의 유일한 저장소로 사용하지 않는다. 새 적용본과 편집 초안을 별도 데이터로 구분해야 한다.

### 5.2 획득·반환

| 상황 | 수량 처리 제안 |
|---|---|
| 적 처치 | 해당 적의 3~5개 후보에서 가중 무작위 1개를 즉시 인벤토리에 반영하고 알림 |
| 침입·시간 제한으로 미스폰 취소 | 드롭 없음 |
| 초안 편집·취소 | 보유·적용 예약 변화 없음 |
| 적용 성공 | 새 함수 비용으로 예약 교체 |
| 적용 실패 | 기존 함수와 예약 유지 |
| 로봇 삭제 | 함수 제거, 해당 로봇 예약 전부 해제 |
| 다음 스테이지 | 명령어 보유량 유지. 로봇 유지/해제에 따라 예약 정산(D15) |
| 처음부터 재도전 | 시작 지급 상태로 초기화하는 안. 세션 간 영구 보유는 추가하지 않음 |

드롭 후보별 가중치와 100% 드롭 여부는 원문에서 확정되지 않았다. 위 표의 처치당 1개 보장은 제안이며 D15에서 결정한다. 변수·숫자·비교까지 소비형으로 셀지, 기본 도구로 무제한 제공할지는 블록별 비용 데이터로 명시하고 D09/D14에서 확정한다.

## 6. 배치·개발툴·학습 계약

### 6.1 로봇 배치

정비 상태, 배치 상한 미달, 유효한 비점유 배치 지점일 때만 배치 가능하도록 제안한다. 잘못된 지점 드롭은 원위치로 되돌리고 원인을 표시한다. 이동은 출발점 해제와 도착점 점유를 한 번에 수행한다. 삭제는 함수 예약 반환을 포함한다. 이동·삭제·배치 요청은 Combat에서 거부한다(D17).

원문에는 로봇 배치 자원 비용과 배치 방향이 없으므로 추가하지 않는다. A의 격자와 U의 원형 받침대를 함께 참고해 명시적인 배치 지점 컴포넌트를 제안하되 맵 수·지점 수는 미정이다.

### 6.2 개발툴

`errorValue`, `errorStage`, `failureThreshold`, 스킬 범위·피해·쿨타임과 오류 효과 목록을 가진다. 원문 기본 피해 50과 오류 5단계를 기록하고, 임계치 배열·고장 횟수·스킬 자동/수동 발동은 D13에서 확정한다. 오류 값이 바뀔 때 단계와 표시를 함께 갱신한다.

오류 효과는 약 3종이라는 요구만 있으며 확정 목록은 없다. UI 지직거림, 스킬 성능 이상, 로봇 실행 방해 중 어떤 조합을 사용할지 결정한다. 버튼 판독·오류 수정이 불가능할 정도로 필수 UI를 파괴하지 않고, 게임 상태이상 때문에 실행이 막힐 때 전용 이유를 보여주는 것을 제안한다.

### 6.3 학습·힌트

각 스테이지는 학습 목표, 소개 문구, 예제 트리, 지급 블록, 필요 구조 검사, 힌트 목록을 갖는다. 첫 웨이브는 해당 개념을 사용하도록 설계한다. 필수 구조 블록은 랜덤 드롭 외에 보장 지급하는 안이다.

힌트는 정비 편집 화면에서 유효한 편집·적용 없이 머문 시간을 기준으로 제공할 것을 제안한다. 기준 초, 첫 힌트 내용, 반복 빈도는 D15 미정이다. 단순 조작 안내부터 제공하고, 사용자가 작성한 블록을 자동 변경하지 않는다.

## 8. 데이터와 모듈 설계 제안

### 8.1 정적 데이터

| 데이터 | 주요 필드 | 제약 |
|---|---|---|
| StageDefinition | id, learningId, robotLimit, waveIds, initialGrants | stage ID는 1~4, 로봇 수는 정수 |
| WaveDefinition | id, spawnEntries, spawnDeadline | 스폰 항목에 enemyId/pathId/count/interval/delay, 음수 금지 |
| RobotDefinition | id, prefab, damage, attackInterval, detectionRange, attackRange, slow | 로봇 2종, 참조 누락은 구성 오류 |
| EnemyDefinition | id, prefab, maxHp, speed, leakError, dropTableId, traits | 일반 적 3종, 보스 구분은 D16 |
| BlockDefinition | kind, category, inputTypes, outputType, countPolicy, unlockStage | 기존 enum 값 보존, 추가 타입은 충돌 없이 확장 |
| DropTable | candidates(blockId, weight) | 후보 3~5, 가중치 0 이상·합 0 초과 |
| LearningDefinition | objective, examples, grants, validationRules, hints | 미지원 API 예제 금지 |
| BaseDefinition | damage, cooldown, range, errorThresholds, failureThreshold, effects | 기본 피해 50, 단계 5, 경계값 단조 증가 |

이름은 책임 설명용이며 모든 항목을 별도 프레임워크나 클래스로 분리해야 한다는 뜻은 아니다. ScriptableObject 등 Inspector에서 편집 가능한 데이터로 구현할 것을 제안한다.

### 8.2 실행 데이터와 경계

| 데이터 | 내용 |
|---|---|
| SessionState | 상태, 스테이지·웨이브, 오류량, 획득 인벤토리 |
| RobotState | ID, 배치점, 적용 함수 버전, 블록 예약, 실행 상태 |
| ProgramDraft | 편집용 트리, 블록별 안정 ID, 편집 좌표, 진단 목록 |
| AppliedProgram | 검증된 트리 복사본, 버전, 비용, 표시용 Python, 블록-행 대응 |
| ExecutorState | 현재 노드, 변수, 제어 스택, 대기 시각, 보호 예산 |
| EnemyState | ID, 타입, 경로 진행, HP, 이동 상태, 둔화, 종결 상태 |

스테이지 간 유지가 필요한 데이터는 세션이 소유한다. 씬 UI 오브젝트 자체를 저장 데이터로 삼지 않는다. 디스크 저장·불러오기는 D18 별도 결정이며 이번 기획에서 완료된 기능으로 가정하지 않는다.

### 8.3 책임과 연결

| 책임 | 입력 | 출력 |
|---|---|---|
| 게임 흐름 | 웨이브 종료·오류 변화·시작 요청 | 상태 전환·초기화 |
| 웨이브/적 | 스폰 데이터·경로 | 적 생성·처치·침입·생존 수 |
| 전투/로봇 | 실행기 행동, 적용 스탯 | 피해·둔화·쿨타임 |
| 블록 편집/검증 | 사용자 트리 | 진단·Python 표시·검증된 트리 |
| 함수 적용 | 로봇 ID·초안·인벤토리 | 적용 성공/실패·예약 교체 |
| 실행기 | 적용 트리·게임 관찰값 | Attack/Wait 요청·실행 위치·Fault |
| HUD/학습 | 상태·진단·선택 로봇 | 표시·입력 요청 |

단일 C# 실행 흐름에서 이 책임을 연결하는 것으로 시작한다. 네트워크, 전역 서비스 검색, 외부 Python 서버는 요구하지 않는다.

## 9. Unity 통합 원칙과 현재 차이

씬·프리팹·Inspector 수정은 프로젝트 작업 규칙에 따라 Unity MCP를 사용한다. 필수 참조는 직렬화된 필드로 노출하고 MCP로 연결한다. 임시 Editor 스크립트, 런타임 Find/Resources.Load/자식 검색으로 누락을 덮는 대체 경로를 만들지 않는다. 적·탄환 등 실제 게임 규칙상 필요한 프리팹 생성은 가능하다.

Unity MCP로 연결할 대상 예: 상태 관리자와 웨이브 관리자, 경로와 스폰 지점, 개발툴, 로봇 프리팹·배치점, 팔레트·편집 패널·HUD 참조. 기술 설계상 컴포넌트를 확정한 뒤 실제 Inspector 필드 목록으로 세분화한다. 기존 씬·프리팹 구조는 보존하고 변경 범위를 명시한다.

| 항목 | 이번에 읽은 소스/문서의 상태 | 후속 구현 또는 검증 |
|---|---|---|
| 편집 UI | 자유 배치·중첩·드래그와 Python 표시 기록 존재 | 제품 레이아웃·수량·로봇 선택 연결 |
| Compile/Apply | Python 문자열 생성 및 Console 출력, 이벤트 | 검증된 트리 적용·로봇 실행기 연결 |
| while | 조건 없는 while True 문자열 생성 | 조건형 반복과 실행 한도, D07 |
| 적 정보 | Enemy.get_distance는 XY 위치 계산 | 게임 평면 및 HP/Count/Speed 계약 |
| 함수 수량·교체 | 현재 Apply만으로 자원 트랜잭션 확인 불가 | 인벤토리·예약·적용본 분리 |
| 전투·보스·웨이브 | 이번 열람 범위로 통합 동작 확인하지 않음 | Unity MCP로 실제 상태 조사 후 구현 상태 판정 |

기존 `IDE.unity`용 `PythonBlockCompiler`와 `CodeBlock.unity`용 `PythonTreeCompiler`는 구분한다. 실제 기능 수정 후 Unity 컴파일·도메인 리로드를 기다리고 MCP 재연결, Console 오류 및 Inspector 필수 참조를 검증한다. 이번 작업은 문서만 작성하므로 Unity 기능 검증을 새로 통과했다고 보고하지 않는다.

성능 목표 제안은 합의한 기준 PC에서 1920×1080, 60 FPS다. 기준 하드웨어와 최대 동시 적·로봇·블록 수가 미정이므로 달성 상태를 표기하지 않는다. 최악의 콘텐츠 배치와 잘못된 반복문에서도 메인 스레드가 무한 점유되지 않는 것을 별도 필수 검사로 둔다.

기존 컴파일러 검사는 `Tests/BlockCoding/`의 C#·Python 테스트를 활용할 수 있다. 문자열 문법 검사만으로 게임 실행 일치성을 인정하지 않고, AST 실행 결과와 표시 코드의 제한된 참조 실행 결과를 동일 관찰값으로 비교한다. 임의 사용자 문자열 실행으로 확장하지 않는다.

## 11. 구현 착수 순서와 완료 정의

1. D01~D09 및 D14를 우선 결정하고, 목표 API·실행 의미·자원 정책을 고정한다.
2. 현재 씬을 MCP로 조사해 재사용할 편집기와 전투 구성 요소를 확인한다.
3. 한 로봇·한 적·한 경로로 함수 적용→실행→피해→처치→드롭을 연결한다.
4. 정비·수량 예약·재적용·웨이브 전환·오류 누적·재시작을 연결한다.
5. 4개 학습 단계, 2종 로봇·3종 적·보스와 UI를 확장한다.
6. 수용 기준, Unity Console/Inspector, 승인된 시연 시간과 초보자 학습 경험을 검증한다.

완료는 생성된 Python이 화면에 보이는 상태가 아니라, 사용자가 블록을 변경하고 적용한 결과가 실제 전투에 일관되게 반영되며 승패와 재도전까지 이어지는 상태다. 문서 결정 목록의 미해결 항목과 테스트 미실행 항목은 완료 보고에서 별도로 남긴다.
