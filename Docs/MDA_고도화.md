# MDA 고도화

브랜치 `claude/mda-upgrade`. 사용자 경험을 MDA(Mechanics → Dynamics → Aesthetics) 순서로 다듬는 반복 작업의 기준 문서다. 반복마다 아래 백로그 맨 위 항목을 하나 골라 구현·검증·커밋하고, 맨 아래 "반복 기록"에 한 줄을 남긴다.

## 목표 미학 (Aesthetics)

대상은 코딩을 처음 접하는 대학생이다. 우선순위 순서:

| 순위 | 미학 | 이 게임에서의 뜻 |
|---|---|---|
| 1 | Discovery(발견) | "내 코드가 이렇게 움직였구나"를 스스로 알아낸다 |
| 2 | Challenge(도전) | 배운 문법으로 웨이브를 막아 낸다. 실패해도 다시 해 볼 만하다 |
| 3 | Expression(표현) | 같은 웨이브를 내 방식의 코드·배치로 푼다 |
| 4 | Fantasy(판타지) | 개발툴 코어를 오류 코드로부터 지키는 개발자와 로봇 동료 |

## 원하는 다이내믹 (Dynamics)

**가설 → 코드 → 관찰 → 수정**의 짧은 고리. 플레이어가 결과를 보고 "어느 로봇이, 왜" 못했는지 읽을 수 있어야 고리가 돈다.

## 현재 메커닉의 문제 (2026-11-03 진단)

| # | 문제 | 깨지는 고리 | 해당 미학 |
|---|---|---|---|
| P1 | 웨이브 결과가 `처치 / 돌파 / 잔여 적`뿐. 로봇별로 무엇을 했는지 모른다 | 관찰 → 수정 | Discovery |
| P2 | 반복 해금 전 함수가 웨이브당 5회만 실행되는 숨은 규칙. 다 쓰면 로봇이 멈추는데 전투 화면에 안 보인다 | 관찰 | Discovery |
| P3 | 패배하면 스테이지 1웨이브부터, 배치·코드 전부 초기화 | 수정 → 재도전 | Challenge |
| P4 | 스테이지 2와 3의 웨이브 편성이 완전히 같다. 웨이브 주제(감속, while 등)가 해법이 되도록 짜여 있지 않다 | 코드 → 결과 | Challenge, Discovery |
| P5 | 스테이지 2·3에는 목표 줄·안내가 없다. 2-1에서 for가 열리면서 함수 실행 규칙이 바뀌는데 설명이 없다 | 가설 | Discovery |
| P6 | 클리어 여부만 저장. 더 잘 막을 이유(별·기록)가 없다 | 재도전 | Challenge, Expression |
| P7 | 코인 사용처가 레벨업(최대 2)뿐 | 선택 | Expression |

## 백로그 (위에서부터 진행)

| 순서 | 항목 | 문제 | 상태 |
|---|---|---|---|
| 1 | 웨이브 결과 브리핑: 로봇별 공격·피해·처치·함수 실행 횟수, 가장 큰 원인 한 줄 진단 | P1, P2 | 완료 |
| 2 | 패배 시 "이 웨이브 다시": 웨이브 시작 시점의 배치·코드·레벨·코인·코어 체력으로 복귀 | P3 | 진행 |
| 3 | 전투 중 로봇 머리 위 상태: 함수 n/5 소진, 사거리 밖 대기, 코드 오류 | P2 | 대기 |
| 4 | 스테이지 2·3 웨이브 재설계(주제가 해법이 되게) + 웨이브마다 목표 줄 | P4, P5 | 대기 |
| 5 | 2-1 반복 해금 안내(함수 실행 규칙 변화) | P5 | 대기 |
| 6 | 별 등급(코어 체력 기준)·최고 기록, 결과 화면과 스테이지 맵 표시 | P6 | 대기 |
| 7 | 코인 사용처 확장 검토 | P7 | 대기 |

## 작업 규칙

- 규칙 계산은 `DefenseSimulation`·`DefenseProgram`(Unity 비의존)에 두고 헤드리스 검사(`Tests/Defense`)로 확인한다.
- Stage 1 튜토리얼 대사·흐름(`Tutorial_1-1~1-4`)은 기획 원본이 있으므로 깨지 않는다. 바꿔야 하면 [임시변경점.md](임시변경점.md)에 적는다.
- 검증: 헤드리스 검사 3종 + Unity 배치모드 컴파일(에디터가 꺼져 있을 때).
- 반복마다 이 브랜치에 로컬 커밋한다. 푸시는 하지 않는다. 작업과 무관한 미커밋 변경(폰트 asset, ProjectSettings 등)은 커밋에 넣지 않는다.
