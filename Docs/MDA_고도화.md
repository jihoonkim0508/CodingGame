# MDA 고도화

브랜치 `claude/mda-upgrade`. 사용자 경험을 MDA(Mechanics → Dynamics → Aesthetics) 순서로 다듬는 반복 작업의 기준 문서다. 반복마다 아래 백로그 맨 위 항목을 하나 골라 구현·검증·커밋하고, 맨 아래 "반복 기록"에 한 줄을 남긴다.

## 목표 미학 (Aesthetics)

대상은 코딩을 처음 접하는 대학생이다. 우선순위 순서:

| 순위 | 미학 | 이 게임에서의 뜻 |
|---|---|---|
| 1 | Discovery(발견) | "내 코드가 이렇게 움직였구나"를 스스로 알아낸다 |
| 2 | Challenge(도전) | 배운 문법으로 웨이브를 막아 낸다. 실패해도 다시 해 볼 만하다 |
| 3 | Expression(표현) | 같은 웨이브를 내 방식의 코드·배치로 푼다 |
| 4 | Fantasy(판타지) | 개발툴 코어를 오류 코드로부터 지키는 개발자와 로봇 동료 |

## 원하는 다이내믹 (Dynamics)

**가설 → 코드 → 관찰 → 수정**의 짧은 고리. 플레이어가 결과를 보고 "어느 로봇이, 왜" 못했는지 읽을 수 있어야 고리가 돈다.

| P11 | 전투에 소리가 전혀 없다(튜토리얼 경고음만). 공격이 맞았는지·적이 빠져나갔는지를 귀로 알 수 없다 | 관찰 | Sensation, Fantasy |
| P13 | 스테이지 도중에 나갈 길이 없다(Esc는 배치 취소뿐, 스테이지 맵은 5웨이브를 다 깨야 열림). 소리를 끌 수도 없다 | 선택 | Expression(자율) |
| P14 | 브리핑의 '전사형 2'가 맵의 어느 로봇인지 알기 어렵다 | 관찰 → 수정 | Discovery |
| P12 | (기획 확인) Stage 2에는 `while`·`wait()`이 없어, `for` 안에서 거리 조건으로 공격 시점을 고르면 적이 멀 때 반복 횟수가 바로 소진된다. 2-2 목표 '거리 기준값으로 공격 시점 정하기'와 충돌 | 코드 → 결과 | Challenge |

## 2차: 보이는 경험 고도화 (2026-11-03~)

1차(반복 1~13)는 규칙·결과 설명을 고쳤지만 빌드를 켜 보면 첫 10분이 거의 그대로였다(타이틀·맵·1-1 대사·HUD·연출 변화 없음).
2차는 **플레이어가 첫 세션에서 보고 듣고 읽는 것**(UI, 콘텐츠, 대사, 체감되는 시스템)을 고친다. 내부 로직은 보이는 변화에 필요할 때만 바꾼다.

플레이 뒤 피드백: "달라진 게 없어 보인다, 대사가 개발자 관점이다, UI 스타일이 그대로다, 소리·목소리가 없다". 하나씩 고치지 않고 한 번에 갈아엎었다.

## 작업 규칙

- **2차부터 반복마다 플레이어가 알아챌 수 있는 변화**를 하나 이상 만든다. 고치기 전후를 `ScreenTour`(Tools/Develop/화면 캡처 투어, 창 모드 에디터 `-executeMethod`)로 찍어 눈으로 확인한다. 결과는 `TestResults/Editor/tour/`(커밋하지 않음).
- 대사는 원본 `Docs/flow_stage1/tutorial_stage1_대본.md`를 고치고 `TutorialSequenceBuilder`로 asset을 다시 만든다. 기획 검토를 위해 바꾼 줄을 [임시변경점.md](임시변경점.md)에 적는다.
- 규칙 계산은 `DefenseSimulation`·`DefenseProgram`(Unity 비의존)에 두고 헤드리스 검사(`Tests/Defense`)로 확인한다.
- 검증: 헤드리스 검사 3종 + Unity 컴파일 + ScreenTour(에디터가 꺼져 있을 때).
- 반복마다 이 브랜치에 로컬 커밋한다. 푸시는 하지 않는다. 작업과 무관한 미커밋 변경(폰트 asset, ProjectSettings 등)은 커밋에 넣지 않는다.
